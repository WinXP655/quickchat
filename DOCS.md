# QuickChat - Technical Architecture & Implementation

This document describes the internal design, threading model, protocol, and repository structure of QuickChat.\
*For user-facing features, build instructions, and history, refer to `README.md`.*

## Repository Structure
The project is intentionally kept flat. There are no nested source folders. The repository consists of the main source file, resource scripts, assets, and build tools.

### 1. Source Code
- **`quickchat.c`**: The entire application. A single-file monolith containing the UI, network logic, settings, and logging.
- **`key.h`**: Contains the XOR obfuscation key (or is generated by the keygen scripts). Included directly into `quickchat.c`.

### 2. Resources (`.rc` and Assets)
The UI is built using standard Windows resources. These are compiled by `windres` (MinGW) and linked into the final `.exe`.
- **`resources.rc`**: The main resource script. It embeds the icon (`icon.ico`), version info (`VERSIONINFO`), and the application manifest (`quickchat.manifest`).
- **`start.rc`**: The Mode Selection dialog (Host / Join / XOR / Logging).
- **`servconn.rc`**: The Client Connection dialog (IP input).
- **`hostinfo.rc`**: The Host Info dialog (shows the local IP to share).
- **`about.rc`**: The About dialog.
- **`compinfo.rc`**: The Computer Info dialog (shows local/remote IP, names, protocol status).
- **`quickchat.manifest`**: XML file declaring DPI awareness and Common Controls v6 dependency (required for visual styles).

### 3. Assets
- **`icon.ico`**: The application icon.
- **`join.wav`, `leave.wav`, `newmsg.wav`**: Notification sounds. They are **not** embedded in the `.exe`; they must be placed next to the executable.

### 4. Build and Tooling
- **`build.bat`**: The build script (supports `/clean`, `/pack`, `/minbuild`, `/rekey`).
- **`7z.exe`**: Used by the build script to create the final `.zip` distribution package.
- **`keygen.py` / `keygen_fixed.py`**: Python scripts to generate a new XOR key and write it to `key.h`. `keygen_fixed.py` allows using a specific custom key.
- **`readme.txt`**: The user-facing readme included in the `.zip` package.

## Project Structure
QuickChat is a single-file application (`quickchat.c`, ~2000 lines). This is a deliberate architectural choice to keep the build process extremely simple and to avoid dependency hell.\
The code is organized into logical sections using comment banners (Headers, Defines, Globals, Prototypes, Entry Point, Infrastructure, Settings, Utilities, Network, UI, Dialogs, Files).

## Threading and Synchronization Model
The application relies on a strict two-thread model. Understanding this is critical to understanding the code.

### 1. The UI Thread (Main)
Owns all window handles (`hWndGlobal`, `hEdit`, etc.). It runs the standard Windows message pump (`GetMessage`, `DispatchMessage`). **Rule:** No other thread is allowed to call UI functions directly.

### 2. The Receive Thread
Created via `_beginthreadex`. It runs `ReceiveMessages()` and blocks on `recv()`.
- **Timeout Dependency:** The socket uses `SO_RCVTIMEO` (5 seconds). Without it, `recv` would block forever, and `shutdown()` would not be able to wake it up, causing a deadlock on exit.
- **State Sync:** It checks `is_running` using `InterlockedCompareExchange`.

### 3. UI Proxy (Asynchronous Communication)
The Receive Thread cannot touch HWNDs. It sends custom messages (`WM_APP_ADDMSG`, `WM_APP_DISABLE`, `WM_APP_FLASH`) to the UI Thread. It allocates a copy of the string, passes it via `PostMessage`, and the UI thread frees the memory.

## Network Protocol (QC/QCS)
QuickChat uses a custom, TCP-based protocol with optional XOR obfuscation.

- **Ports:** 65501 (XOR enabled) and 65502 (Plaintext).
- **Handshake:** The client connects and sends `QC:<ComputerName>\0` (UTF-8). The server validates the `QC:` prefix and packet size, then replies with its own name in the same format.
- **Packet Boundaries:** The protocol relies on the assumption that one `send()` equals one `recv()`. `TrimIncompleteUTF8()` is used to safely truncate incomplete multi-byte characters at the end of a TCP packet.
- **XOR Key:** Stored in the stack during execution and wiped with `memset`. It is split into multiple arrays to obfuscate its presence.

## Shutdown and Cleanup Sequence
The most sensitive part of the application is `CleanupAndExit()`. The exact order of operations prevents deadlocks and race conditions:
1. **Double-call protection:** Check and set `already_exiting` via `InterlockedExchange`.
2. **Stop Thread:** Set `is_running = 0` (Interlocked).
3. **Wake Socket:** Call `shutdown(client_socket, SD_BOTH)`.
4. **Wait:** Call `WaitForSingleObject(hReceiveThread, THREAD_WAIT_MS)` to ensure the Receive Thread has exited.
5. **Close Socket:** Call `closesocket()` **only after** the thread is dead.
6. **Finalize:** Close logs, call `WSACleanup()`, free GDI resources, and call `PostQuitMessage()`.

## Security and Resilience
- **Input Filtering:** The server strictly validates the handshake prefix. It drops connections that send garbage (empty data, oversized packets, or invalid prefixes).
- **Crash Handling:** `CrashHandler` is installed via `SetUnhandledExceptionFilter`. It catches unhandled exceptoions, writes the error code and address to `crashlog.txt`, and prevents silent process termination.
- **Limits:** Message edit box is limited to 4095 characters. The buffer is 8192 characters (Unicode).

## Build Configurations
- **Release:** Optimized for size (`-Os`, `-ffunction-sections`). Stripped of debug symbols. Vista+ subsystem. Designed for end-users.
- **MinBuild:** Fast and dirty compilation. No optimizations, console window attached, missing dialogs (About, Computer Info) and resources. Designed for testing logic quickly.

## Architectural Limitations
- **1:1 Only:** No multi-client server or group chats.
- **No Authentication:** XOR is obfuscation, not real encryption. There are no passwords or keys exchange.
